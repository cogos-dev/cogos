## Context

CogOS accumulates research insights across multiple intellectual lineage threads —
connections between established science (Spencer-Brown, Maturana/Varela, Pattee,
Rosen, Friston, von Foerster, L. Kauffman) and the working theoretical claims
of the broader research framework. These connections live in the substrate's
semantic memory sector as individual cogdocs, but there is no coherent mechanism for:

1. **Maintaining tier labels** (Tier 1 = established science → Tier 4 = speculative cosmological claims)
2. **Tracking public exposure risk** for each node before external communication
3. **Generating projection views** (bibliography, pedagogical descent, convergence map, etc.) from the node corpus
4. **Watching for corpus changes** and re-generating projections automatically

The lineage corpus is operationally live — it grows as new insights are added and
as correction sweeps validate or falsify claims. Static hand-curated projections
go stale. The substrate's existing `Reconcilable` pattern (ADR-092 §4) is the
correct tool for this problem.

### Problem statement

The observatory pattern requires a managed-reconciliation loop that:
- Reads node cogdocs from a well-defined location
- Computes what projection files differ from what the nodes imply
- Applies the projection writes atomically and idempotently
- Watches for node-level changes and re-runs the loop
- Reports health via the three-axis status model (ADR-092)

This is exactly the Reconcilable contract. The decision is to implement it, not to
build a bespoke pipeline.

## Decision

Establish the **Lineage Observatory** as a substrate primitive, implemented via
the `ProjectionReconciler` type in `internal/engine/projection_reconciler.go`.

### §1 — Observatory location

The canonical observatory lives at:

```
$workspace/.cog/mem/semantic/lineage/
├── SCHEMA.md           # canonical frontmatter fields + edge type reference
├── nodes/              # one cogdoc per node (threads + antecedents)
├── projections/        # generated by ProjectionReconciler (NOT hand-edited)
└── observatory.cog.md  # hub projection (generated by hub-projection reconciler)
```

No new storage layer is introduced. The observatory reuses the existing cogdoc format
with three new frontmatter fields:

| Field | Type | Required | Meaning |
|-------|------|----------|---------|
| `tier` | 1\|2\|3\|4 | Yes | Epistemic tier (established → speculative) |
| `public_exposure_risk` | high\|medium\|low\|none | Yes | Pre-publication risk level |
| `demotion_template` | string | For tier ≤ 3 | Public-safe framing for external communication |

### §2 — Tier semantics

| Tier | Meaning | Safe to cite externally? |
|------|---------|--------------------------|
| 1 | Established science; published, peer-reviewed | Yes — directly |
| 2 | Structural parallel; well-grounded but not peer-reviewed as stated | Yes — with framing |
| 3 | Working hypothesis; operator-developed claim needing validation | Only with demotion template |
| 4 | Universal/cosmological claim; speculative scope | Requires explicit disclaimer |

### §3 — ProjectionReconciler as substrate primitive

`ProjectionReconciler` (in `internal/engine/projection_reconciler.go`) implements
the seven-method `reconcile.Reconcilable` contract per ADR-092 §4:

| Method | Behavior |
|--------|----------|
| `Type()` | Returns `"lineage-projection-<kind>"` |
| `LoadConfig()` | Discovers nodes/ directory from workspace root; creates projections/ if needed |
| `FetchLive()` | Reads all `.cog.md` files from nodes/, parses frontmatter; read-only |
| `ComputePlan()` | Compares current projection file content against generated content; pure function |
| `ApplyPlan()` | Writes projection file atomically (tmp + rename); idempotent per ADR-092 §3 |
| `BuildState()` | Constructs state from live node list + projection file path; pure function |
| `Health()` | Returns three-axis status reflecting last reconcile phase |

The reconciler's lifecycle follows the state machine:

```
Starting → Live (after first successful apply)
Live → Stalled (no changes detected; synced)
Live/Stalled → Detached (nodes/ dir unreachable)
Live/Stalled → Crashed (unrecoverable error)
Crashed → Starting (operator restart)
```

### §4 — Watch/trigger mechanism

`ProjectionWatcher` (in the same file) watches the `lineage/nodes/` directory
for file system events using `fsnotify`. On any WRITE, CREATE, or REMOVE event,
it debounces for 500ms and then calls the trigger function. If `fsnotify` is
unavailable, it falls back to polling at a configurable interval (default 5s).

The watch mechanism is **not** ledger-event-based in the initial implementation.
A future RFC may add ledger-event subscription as a secondary watch path for
multi-node observatory synchronization.

### §5 — Six canonical projections

Six `ProjectionReconciler` instances are registered at init time via
`RegisterProjectionProviders()`:

| Projection kind | Provider type key | What it generates |
|----------------|------------------|-------------------|
| `pedagogical-descent` | `lineage-projection-pedagogical-descent` | Curriculum from Tier 1 antecedents to Tier 3/4 claims |
| `bibliography` | `lineage-projection-bibliography` | All Tier 1 nodes, citable references |
| `lineage-chain` | `lineage-projection-lineage-chain` | grounds/extends/supersedes traversal |
| `convergence-map` | `lineage-projection-convergence-map` | All convergence edges |
| `open-questions` | `lineage-projection-open-questions` | open-gap edges + Tier 3/4 nodes |
| `outreach-status` | `lineage-projection-outreach-status` | Exposure audit + demotion templates |

### §6 — Correction protocol

When a corpus document contains a factual error:

1. Add `corrected: <YYYY-MM-DD>` and `correction_note: "<text>"` frontmatter to the affected node.
2. If the source document (outside lineage/) needs patching, patch in-place with the same frontmatter flag.
3. The ProjectionReconciler will pick up the correction on the next reconcile cycle.

**Canonical correction (2026-05-16):** A correction sweep validated the canonical values in the lineage node corpus for the FEP cost at the eigenform operating point. No documents were found incorrectly conflating the distinct quantities involved. The canonical node document is correct.

### §7 — What this ADR does NOT do

- Does not modify ADR-091 or ADR-092.
- Does not introduce a new storage layer (reuses cogdoc + frontmatter).
- Does not auto-merge the ADR or any code PR — operator review required.
- Does not claim the observatory manages nodes outside `lineage/nodes/` (the broader `semantic/insights/` corpus is read-only from the observatory's perspective).
- Does not add new MCP tools — all operations use existing `cog_search_memory`, `cog_grep_files`, `cog_query_field`, `cog_write_cogdoc`, and `cog_patch_frontmatter`.

## Consequences

### Positive

- Projections regenerate automatically when nodes change; no manual maintenance.
- Tier + exposure fields create a pre-publication safety layer for all research claims.
- The six projection kinds give multiple entry points into the lineage (curriculum, bibliography, convergence, outreach) without duplicating data.
- The `ProjectionReconciler` follows the established `Reconcilable` pattern; no new architectural primitives needed.
- Correction sweep is substrate-native: `corrected:` frontmatter flag + reconciler re-run = corrected projection.

### Neutral

- The observatory hub (`observatory.cog.md`) is generated, not hand-edited; human-readable but not human-maintained.
- The six projection kinds cover the current use cases; new projection types require a new `ProjectionKind` + generator function + registration.

### Negative / Trade-offs

- `ProjectionWatcher` uses fsnotify, which is OS-dependent; the polling fallback reduces responsiveness.
- The six reconcilers register at process init via `init()`, adding startup cost proportional to the number of projections.
- The correction protocol requires manual `corrected:` frontmatter patching; there is no automated claim-validation pipeline.

## Alternatives Considered

**Hand-curated projections (rejected):** Static files go stale as the node corpus grows. The observatory pattern is specifically motivated by the need for automatic refresh.

**New MCP tool for projections (rejected):** Existing tools cover all operations. Adding new MCP tools would grow the surface area without adding capability.

**Ledger-event-based watch (deferred):** More substrate-native than fsnotify but requires event kind registration and subscription wiring. The fsnotify approach is sufficient for local use; ledger-event subscription is the upgrade path for multi-node scenarios.

**Storing tier/exposure in a separate index (rejected):** Per ADR-092 §5 (schema minimalism guidance), project at read time from frontmatter rather than storing derived fields. The `ProjectionReconciler` IS the projection layer.
